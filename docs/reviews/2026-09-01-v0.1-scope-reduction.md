# Boxwarden v0.1 scope-reduction proposal

Date: 2026-09-01

Status: Superseded as an implementation plan by
`docs/superpowers/plans/2026-09-01-boxwarden-v0.1.md`. It remains historical
scope-reduction input; its direct-authentication deferral was superseded by the
approved V0.1 real-work authentication requirement.

## Recommendation

Ship v0.1 as the smallest trustworthy lifecycle manager for one qualified local
full-GUI disposable workstation. Do not make the first release also solve
golden construction, generalized persistence, host-tree proposals, credential
brokering, or rich artifact admission.

The release should prove the differentiating thesis:

> Give the autonomous agent a whole disposable computer, not merely a sandboxed
> shell.

Task 0 already proved the physical platform. v0.1 should productize the path
from an explicitly configured, already-qualified domain golden to a running,
inspectable, stoppable, and safely destructible workstation.

This is a release slice through M1A, not a redefinition of M1A completion.
Features marked defer remain valid architecture and can follow without
pretending v0.1 implemented them.

## v0.1 user contract

Required routine commands:

    boxwarden --domain DOMAIN session create NAME
    boxwarden --domain DOMAIN session start NAME
    boxwarden --domain DOMAIN session status NAME
    boxwarden --domain DOMAIN session ssh NAME
    boxwarden --domain DOMAIN session stop NAME
    boxwarden --domain DOMAIN session destroy NAME

Required one-time onboarding may include:

    boxwarden --domain DOMAIN identity init
    boxwarden --domain DOMAIN golden register QUALIFIED_TART_OBJECT
    boxwarden --domain DOMAIN validate host

golden register is deliberately narrower than a builder or promotion engine. It
binds one exact stopped, clone-ready, domain-specific Tart golden and its
existing Task 0/guest-definition evidence into domain configuration. It must
refuse a mutable/running object, wrong qualified toolchain, missing domain CA
anchor, or incomplete clone-ready identity evidence. Construction remains the
documented operator/bootstrap workflow until later automation replaces it.

## Minimum viable behavior

### Control plane and domains

- A Go binary with strict configuration and JSON decoding.
- An explicit lowercase domain on every operation; no first/default/cross-domain
  fallback.
- Domain-owned private runtime, state, lock, log, SSH CA, known-host, golden
  reference, and credential-reference paths.
- Argv-only bounded external execution with sensitive-input redaction and no
  host shell.
- Exact identifiers and paths persisted before backend mutation.

### Tart lifecycle

- A small neutral backend contract and one Tart 2.32.1 adapter.
- Exact Task 0 Tart + Softnet 0.19.0 launch policy.
- A production-safe integrity-bound way to execute the qualified privileged
  Softnet artifact; a mutable Homebrew path does not qualify.
- Task 0's private Screen-held serial relay on every normal launch.
- No host filesystem, clipboard, audio, display-server, Docker, forwarding,
  port, extra-disk, bridged, or nested integration.
- Reconciled create/start/status/stop/destroy with intent-before-mutation,
  per-session locks, idempotent retry, and explicit partial/orphan states.
- Destruction targets only the exact recorded backend object.

### Identity and readiness

- A distinct host-only user-CA private key per domain and its public anchor in
  the registered golden.
- Short-lived session/principal-bound SSH certificates.
- Serial-observed clone host-key pinning and management address refresh.
- Random clone MAC plus verified machine/SSH/DHCP identity regeneration.
- Host IANA time-zone detection, guest apply, and readback on every
  create/start before ready.
- GUI readiness/status consistent with Task 0's Aqua and long-lived Tart process
  observations.

### Session classes and credentials

- Clean interactive and quarantine are central session policy classes.
- Quarantine rejects Boxwarden profile/normal-secret injection and reusable
  provider/Git credentials, while warning that manual login can defeat the
  intended posture.
- v0.1 may rely on interactive guest-local browser/desktop/CLI login. A
  Boxwarden API-key injection command is not required for the first release.
- Documentation recommends one provider per high-isolation session and explains
  that guest root combines all identities and artifacts intentionally present.
- Compromised destroy trusts no guest report, performs no credential/profile
  operation, identifies affected credential references, and deletes only the
  recorded backend object.

### Practical Git and loss prevention

The agent works on a guest-local clone obtained through public access or a
manual/short-lived guest credential. v0.1 supports registration of explicit Git
worktree paths and a minimal accidental-loss check:

- modified and untracked files;
- upstream presence;
- ahead/unpushed commits;
- remote reachability when the configured policy can prove it.

Output labels guest-observed versus host-corroborated facts. This is not a
security claim against hostile guest root. If project state is unregistered,
unreachable, or unverified, normal destroy refuses. A conspicuous exact
domain/session --allow-data-loss acknowledgement remains available.

Defer non-Git durability adapters, automatic push, generic host export, and a
rich policy engine. This minimum is enough for practical Git use without
pretending every disposable disk is safely recoverable.

### Validation and recovery

- Host validation for architecture, exact qualified toolchain, privileged
  Softnet binding, domain-root isolation, SSH CA, registered golden, serial
  dependencies, and unsupported environment status.
- Session validation/status for intent versus observation, identity, address,
  time zone, network policy, provider warning, Git-loss state, and
  partial/orphan errors.
- End-to-end acceptance for one lifecycle, restart, concurrent isolation,
  quarantine rejection, normal destroy blocker, compromised destroy, and
  recreation.
- Honest reporting of ADR 020's unqualified IPv6-only environments.

## Relationship to the current 12-task plan

Task 0 is complete and is an input, not implementation work.

Approximately **eight of the eleven unfinished current plan tasks** contribute a
critical subset to v0.1:

- Task 1: control plane/domain/runner, reduced CLI resources;
- Task 2: narrow Tart adapter;
- Task 4: only the bounded guest helper and already-qualified guest properties;
- Task 6: lifecycle/reconciliation;
- Task 7: SSH discovery and trust;
- Task 9: only session classes, compromised path, provider warnings, and minimal
  Git durability;
- Task 10: only routine wrappers, validation, recovery, and v0.1 acceptance;
- Task 11: a correspondingly smaller release audit.

Tasks 3, 5, and 8 are removed from the v0.1 critical path. Task 3's exact
Tart/Softnet and golden checks are supplied by existing Task 0 evidence plus
minimal host validation, not by implementing the broad optional-artifact lock.
Task 5's builder/promotion machinery and Task 8's profile system follow later.

These are slices, not executable task boundaries. The canonical plan should be
rewritten only after this scope is approved; attempting to execute eight large
tasks with most steps crossed out would be error-prone.

## Recommended implementation order

### Slice 1: read-only control-plane spine

Implement strict domain config, private paths, bounded argv runner, session
record parsing, fake backend, Tart list parser, and:

    boxwarden --domain test session status NAME

Status is the smallest useful seam test. It exercises common/backend
separation and reconciliation without mutating a VM.

### Slice 2: stopped-object lifecycle

Add golden registration, locks, create from exact clone-ready golden, identity
intent, stop, destroy, retry/fault tests, and compromised destruction. Keep
start out until serial supervision and Softnet privilege are ready.

### Slice 3: qualified running lifecycle

Add the integrity-bound Softnet path, managed serial/Screen supervision,
start/reconcile, DHCP address refresh, host-key evidence, short-lived SSH
certificate, time-zone convergence, and ready status.

### Slice 4: session safety classes

Add quarantine enforcement, provider blast-radius status/warnings, explicit Git
path registration, minimal loss checks, and the data-loss acknowledgement.

### Slice 5: release proof

Add host/session validation, wrappers, property regressions, fault injection,
one full clean lifecycle, one quarantine negative path, one normal loss blocker,
one compromised destroy, recovery, and the v0.1 audit.

## Smallest recommended next implementation pass

Do only Slice 1 on a fresh implementation branch. Its deliverable is a
status-only Go vertical slice with strict domains, private state roots,
consumer-driven fake/backend interfaces, defensive Tart JSON parsing, and
tests. It should not create, start, stop, or delete a VM.

That step is small enough to review, establishes the most consequential package
boundary, and creates the test harness needed for later state-changing
lifecycle work.

## Explicit deferral consequences

- v0.1 users must prepare/register a qualified domain golden through documented
  bootstrap steps.
- No profile or host-tree state survives through Boxwarden.
- Browser/provider login state lives and dies with the VM.
- API keys are not protected by a host broker.
- Normal destruction can be conservative and occasionally require an explicit
  data-loss acknowledgement.
- v0.1 is not called M1A complete; it is the first runnable release on the M1A
  path.

These constraints are visible product limits, not hidden implementation debt.
