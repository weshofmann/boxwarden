# Persistence and encryption

Git provides versioning and distribution, not confidentiality. Sensitive data must be encrypted before it leaves the trusted host, including before it is put in a private Git repository or other remote store.

The default format is age. Public recipients are non-secret and may appear in profile manifests. Each security domain has distinct daily-use and offline recovery recipients; artifacts never inherit or fall back to another domain's recipients. Private age identities remain on the trusted host, outside this repository, profile artifact storage, backend image storage, and disposable sessions. The offline recovery identity is not stored beside the daily-use identity.

M1A supports only named declarative adapters. An adapter fixes the allowed source and destination paths, file types, ownership, modes, size/count limits, confidentiality, execution trust, quiescence requirement, validation, semantic diff, staged apply, and rollback behavior. The initial adapters are:

- `sensitive-markdown-v1`: UTF-8 Markdown below the adapter-owned profile-memory directory; sensitive and declarative but security-sensitive; no executable files or non-Markdown payloads;
- `git-preferences-v1`: a generated Git configuration containing only explicitly allowed non-secret preference keys; aliases, includes, credential helpers, filters, hooks paths, SSH commands, signing-key material, and arbitrary configuration are rejected.

There is no arbitrary archive, opaque state, browser profile, provider session, application database, or generic filesystem adapter in M1A. Known Kindex paths are always rejected.

Capture reads only adapter-allowlisted objects and normalizes them into an adapter-owned candidate. The trusted host re-performs every structural and semantic admission check over the exact received bytes before encryption or candidate creation; guest-side validation exists only to fail early and improve UX. Trusted-host validation rejects absolute paths, `..` traversal, symlinks, hard links, devices, sockets, setuid/setgid material, duplicate paths, destination escapes, unreasonable file counts, unreasonable expanded size, schema violations, and adapter semantic violations. Sensitive bytes are encrypted immediately on the trusted host to every required recipient. Persistent candidate state consists of immutable ciphertext plus a normalized non-secret manifest and review receipt; no persistent plaintext candidate is created.

The candidate record includes security domain, source session, adapter/version, golden revision, tool versions, normalized manifest digest, ciphertext digest, semantic diff or review data, and capture time. Candidate inspection treats every decrypted byte as attacker-controlled: it never writes raw candidate bytes to the terminal or invokes a rich Markdown renderer; it escapes C0/C1 and ANSI/OSC terminal sequences, visibly marks Unicode bidi and zero-width/format controls, reports byte counts and any truncation, and displays the exact normalized-manifest and ciphertext digests beside the review. M1A does not attempt to solve the broader Unicode confusable/homoglyph problem. Approval names those exact digests. It promotes that immutable ciphertext atomically within the same domain; it never re-captures or re-encrypts mutable guest data after review. A replayed approval for different bytes, domain, recipients, profile, adapter version, or destination is invalid.

Restore verifies the approval receipt and both digests before decryption. Trusted-host code validates the exact envelope again before any bytes are admitted to the restore stream. Decryption streams from the trusted host into a fresh guest staging directory owned by the adapter. The guest validates the staged tree and semantic content before applying it as a correctness check, not as a security control protecting the host. Apply is atomic where the destination permits it; otherwise the adapter creates a same-filesystem rollback copy, restores on failure, and reports a non-success result until post-apply validation passes. No restore extracts directly into the live home directory.

There is no automatic mutable-state return synchronization. Session notes and profile changes remain disposable until a human explicitly captures, reviews, and approves them.

Identity and store paths are canonicalized before use. `boxwarden` rejects symlinked identity, candidate, profile-store, repository, backend-artifact, and runtime-state paths; creates identities exclusively with mode `0600`; and creates profile/candidate directories with mode `0700`. Domain path components come only from validated configured IDs, never user-supplied relative paths. It warns or refuses known cloud-synchronized identity locations where detection is reliable. FileVault or equivalent host-disk protection is an explicit host assumption, not something age provides.

Key rotation creates a new daily-use recipient, decrypts each approved artifact with an existing daily or offline identity, re-encrypts it to the new daily plus offline recipients, validates the plaintext and new ciphertext digests, and records a new approval receipt before retiring the old daily identity. The recovery identity is tested periodically without placing it on the host permanently.

For small structured configuration where keys and shape are safe to disclose, a future SOPS plus age convention may be adopted. Restic is a possible later encrypted-backup/retention enhancement, not a Milestone 1A dependency.

Milestone 1A uses an explicitly configured, domain-scoped local `file://` artifact store outside the repository, Tart home, and runtime state. Future remote stores must preserve encryption, domain isolation, immutable candidate identity, origin/approval authenticity, and explicit-approval rules; age encryption alone is not a remote-store approval signature.
